# Rise 音效系统设计

## 1. 目标

为 `Rise` 设计一套以环境发声、玩家接收为核心的音效系统，满足以下目标：

- 环境中的风、营火、落石、绳索点、休息点都可以作为 `3D` 发声源存在。
- 玩家通过自身位置和主相机统一接收环境声音，获得远近、方向、危险感。
- 玩家动作音效和环境音效共用一套事件驱动系统，避免后期到处手写 `AudioSource.Play()`。
- 当前素材未齐时，先把系统结构、事件接口、资产槽位、调参规则搭好，后续直接替换音频资源。
- 兼容当前原型代码规模，先轻量实现，后续再扩展到混音、遮挡、天气和动态音乐。

---

## 2. 核心设计思路

系统分成四层：

1. `Audio Event` 层
   - 定义“发生了什么”，例如抓取成功、滑手、短休、风声增强。
   - 不直接关心音频文件放在哪，也不直接创建 `AudioSource`。

2. `Audio Database / Cue` 层
   - 定义“这个事件应该播什么”。
   - 一个事件可以对应一个或多个 `Clip`、随机音高、随机音量、循环规则、3D范围、Mixer路由。

3. `Audio Runtime` 层
   - 负责真正播放、池化 `AudioSource`、控制优先级、限制同类音效连发。
   - 区分 `2D UI`、`Player Foley`、`World 3D Loop`、`World 3D OneShot`。

4. `Audio Authoring` 层
   - 给场景里的对象挂 `AmbientEmitter`、`RestPointAudioProxy`、`WindZoneAudioEmitter` 等组件。
   - 让关卡布置时可以直接摆放声音，而不是只靠代码硬编码。

## 3. 玩家接收模型

### 3.1 Listener 归属

建议保持一个主 `AudioListener`：

- 挂在 `Main Camera` 上。
- 因为当前游戏是固定相机侧视爬山，声音空间最终应以相机输出为准。
- 玩家只是“逻辑上的接收者”，真正的 Unity 监听器仍然是相机。

### 3.2 玩家接收的逻辑作用

虽然 Unity 的 `AudioListener` 在相机上，但系统层面仍然把“玩家”作为接收中心：

- 玩家位置用于判断呼吸、体力、抓取、滑落等“身体音效”。
- 玩家状态用于驱动近身音效强弱，例如低体力呼吸加强、失手时心跳或喘息抬升。
- 玩家和环境发声体之间的距离用于控制额外逻辑，如危险区风声权重、休息点营火的激活。

建议理解为：

- `Camera = 声音输出耳朵`
- `Player = 声音语义接收者`

## 4. 声音分类

建议从一开始就把声音按总线和职责拆开。

### 4.1 分类

- `Master`
- `UI`
- `Music`
- `Ambience`
- `WorldFoley`
- `PlayerFoley`
- `Tools`
- `Stingers`

### 4.2 当前项目优先级

第一阶段优先做：

1. `Ambience`
2. `PlayerFoley`
3. `Tools`
4. `Stingers`

`Music` 可以先空着或只留一个很轻的底。

## 5. 环境发声体设计

环境音要以“场景物体自己发声”为主，而不是全局单轨背景音。

### 5.1 发声体类型

建议统一抽象成 `AudioEmitter`，再按用途细分：

- `AmbientLoopEmitter`
  - 持续循环
  - 例如高空风声、营火、绳索轻晃

- `SpotOneShotEmitter`
  - 条件触发单次播放
  - 例如落石、冰裂、木牌晃动、营地点火确认

- `ReactiveSurfaceEmitter`
  - 由玩家交互驱动
  - 例如粗糙岩面抓取声、冰面滑手声

- `AreaBlendEmitter`
  - 区域型环境混合
  - 例如某一段山体风更大，玩家进入后平滑提高对应循环层音量

### 5.2 推荐参数

每个环境发声体建议有以下参数：

- `CueId`
- `PlayOnAwake`
- `Loop`
- `SpatialBlend`
- `MinDistance`
- `MaxDistance`
- `Volume`
- `Priority`
- `Cooldown`
- `RandomPitchRange`
- `RandomVolumeRange`
- `FollowTarget`
- `CanVirtualize`

### 5.3 3D 设置建议

对当前侧视攀爬原型，推荐先统一规则：

- `SpatialBlend = 1`
- `DopplerLevel = 0`
- `Spread = 0`
- `Rolloff = Custom` 或 `Logarithmic`

建议距离模板：

- 近场细节音
  - `MinDistance = 1.5`
  - `MaxDistance = 6`
  - 例如抓点摩擦、装备金属碰撞

- 中场场景音
  - `MinDistance = 4`
  - `MaxDistance = 12`
  - 例如营火、绳索装置、局部风口

- 远场氛围音
  - `MinDistance = 8`
  - `MaxDistance = 24`
  - 例如高空风层、远处山谷回响

## 6. 玩家动作音效设计

玩家动作音效虽然和环境互动强相关，但实现上最好走事件系统。

### 6.1 关键动作事件

基于当前 `PlayerClimbController`，建议先定义这些事件：

- `GrabSuccess`
- `GrabFail`
- `HoldLoopStart`
- `HoldLoopStop`
- `Slip`
- `KickLeft`
- `KickRight`
- `FallStart`
- `FallRespawn`
- `ShortRestStart`
- `ShortRestComplete`
- `LongRestStart`
- `LongRestComplete`
- `GoalReached`

### 6.2 事件和当前代码的映射

可以直接从这些位置发事件：

- `TryGrabHand()`
  - 成功抓取时发 `GrabSuccess`
  - 够不到或体力不足时发 `GrabFail`

- `ReleaseHand()`
  - 正常松手时发 `HoldLoopStop`

- `UpdateSlip()`
  - 触发滑手时发 `Slip`

- `UpdateKickInput()`
  - `Q/E` 成功发力时发 `KickLeft / KickRight`

- `PerformRest()`
  - 进入协程发 `ShortRestStart / LongRestStart`
  - 恢复完成后发 `ShortRestComplete / LongRestComplete`

- `RespawnAtCheckpoint()`
  - 发 `FallRespawn`

- `OnTriggerEnter()` 命中 `GoalPoint`
  - 发 `GoalReached`

### 6.3 声音归属位置

玩家动作音效建议分两类：

- 近身动作音
  - 发声位置跟随玩家身体或左右手
  - 例如喘息、布料、踢腿、身体摩擦

- 交互命中音
  - 发声位置在环境接触点
  - 例如左手抓到岩点，声音应来自左手命中的岩壁位置，而不是玩家中心

这点很重要，因为它决定 3D 感是否可信。

## 7. 表面驱动音效

当前项目已经有 `ClimbSurface` 和 `ClimbHold`，这非常适合做“表面材质发声”。

### 7.1 建议新增音频材质枚举

例如：

- `RockRough`
- `RockSharp`
- `Ice`
- `Snow`
- `WoodCamp`
- `MetalAnchor`
- `Rope`

### 7.2 表面音频数据

给 `ClimbSurface` 增加一个轻量引用：

- `SurfaceAudioProfile`

里面定义：

- 抓取命中音
- 持续摩擦循环音
- 滑手音
- 松手音
- 默认音量
- 默认3D距离

这样同一个“粗糙岩面”既有体力参数，也有声音参数，关卡作者很好理解。

### 7.3 好处

- 不同区域的岩壁即使玩法参数相同，也能靠声音区分。
- 冰壁的危险感可以主要靠“更尖、更脆、更滑”的反馈建立。
- 后续扩展天气时，可以只替换 `SurfaceAudioProfile` 而不改玩家逻辑。

## 8. 环境氛围系统

环境氛围不建议只放一个全局风声循环。更好的方案是“全局底噪 + 局部发声体 + 区域增强”。

### 8.1 三层氛围结构

1. 全局底层
   - 一条很轻的高山空气流动底噪
   - 始终存在，音量低

2. 局部3D循环
   - 风口、营火、绳索点、危险裂缝
   - 通过空间位置提供方向感

3. 区域状态增强
   - 到高处、寒冷区、 summit 前风声加剧
   - 通过区域触发或高度参数混入额外层

### 8.2 高度驱动

这个项目很适合做“高度越高，风越强”：

- 读取玩家 `Y` 高度
- 对应提升 `WindHighAltitude` 总线音量
- 同时略微削弱低海拔环境层

建议先做线性插值：

- `y <= 2`：高空风层 `0`
- `y >= 12`：高空风层 `1`

### 8.3 危险状态驱动

当以下情况发生时，提高近身压力音：

- 体力低于阈值
- 只剩一只手抓住
- 进入高滑落概率表面
- 下坠速度大

可影响：

- 呼吸音量
- 风切音量
- 低频压力垫底

## 9. 工具音效设计

当前策划里工具包括 `Anchor` 和 `Rope`，系统上建议提前留接口。

### 9.1 Anchor

建议拆成三个事件：

- `AnchorAim`
- `AnchorPlace`
- `AnchorEngaged`

其中真正优先的是：

- `AnchorPlace`
  - 金属落点确认
- `AnchorEngaged`
  - 抓到免体力点时的稳定确认

### 9.2 Rope

建议拆成：

- `RopeFire`
- `RopeAttach`
- `RopeTension`
- `RopeSlide`
- `RopeRelease`

循环类如 `RopeTension` 不要每帧重播，应由状态进入/退出控制。

## 10. Runtime 架构建议

## 10.1 单例入口

建议一个全局 `AudioService`：

- 持有 `AudioMixer`
- 持有 `AudioCueDatabase`
- 管理 `AudioSource` 对象池
- 提供统一接口：
  - `Play2D(cueId)`
  - `Play3D(cueId, position)`
  - `PlayAttached(cueId, transform)`
  - `StartLoop(handle)`
  - `StopLoop(handle)`

### 10.2 对象池

不要每次 `new GameObject + AudioSource`。

建议：

- `OneShot2D Pool`
- `OneShot3D Pool`
- `Loop Pool`

这样后面连抓、连踢、连滑的时候不会频繁分配。

### 10.3 并发和限流

必须有基础限流，否则抓墙时会非常吵。

建议规则：

- 同一 `CueId` 最短重播间隔 `0.05s - 0.2s`
- 同类事件同屏最大并发数限制
- 超出上限时丢弃低优先级实例

例如：

- `GrabSuccess` 最多同时 3 个
- `Slip` 最多同时 2 个
- `WindLoop` 同类只保留最重要的 1 到 2 个

## 12. 推荐的代码接入方式

为了不让 `PlayerClimbController` 继续膨胀，建议不要把大量音频判断直接塞进去。

### 12.1 推荐拆分

- `PlayerAudioBridge`
  - 监听 `PlayerClimbController` 的动作事件
  - 转换成音频事件

- `WorldAudioEmitter`
  - 挂在场景物体上
  - 描述这个物体怎么发声

- `AudioService`
  - 统一播放

- `AudioCueDatabase`
  - 存配置

### 12.2 最理想的事件流

`PlayerClimbController`
-> 发出 gameplay event
-> `PlayerAudioBridge`
-> 调用 `AudioService`
-> 从 `AudioCueDatabase` 找到对应配置
-> 池化播放

这样后续如果你改动作规则，音效层不用跟着重写。

## 13. 和当前原型的第一阶段对接方案

在不等素材齐的情况下，第一阶段建议只做骨架。

### 13.1 第一阶段目标

- 建立 `AudioCue` 数据结构
- 建立 `AudioService`
- 建立 `PlayerAudioBridge`
- 给 `ClimbSurface` 增加 `SurfaceAudioProfile` 引用位
- 给 `RestPoint`、营火、风口留 `WorldAudioEmitter`
- 场景中保证只有一个 `AudioListener`

### 13.2 第一阶段先接的事件

按收益排序：

1. `GrabSuccess`
2. `Slip`
3. `KickLeft / KickRight`
4. `ShortRestComplete`
5. `LongRestComplete`
6. `GoalReached`
7. `WindLoop`
8. `BreathingLoop`

### 13.3 没素材时怎么占位

- 每个 `Cue` 先允许空数组
- 空素材时静默返回，不报错
- Inspector 中依旧可以提前配好距离、优先级、类别和路由

这样你收素材时只是在 `ScriptableObject` 里补 `Clip`。

## 16. 一些关键实现原则

- 所有动作音效优先绑定“状态变化”而不是 `Update` 轮询。
- 所有近身交互音优先从接触点发声，而不是从玩家中心发声。
- 所有循环音都必须显式开始和停止，不能不断重复 `PlayOneShot`。
- 所有环境氛围都优先做“低音量、多层、空间化”，避免一条大风循环从头播到尾。
- 素材未齐时先把数据结构、事件接口和调参规则立住，后面替换成本最低。

## 17. 对这个项目最合适的落地建议

结合你当前工程体量，我建议不要一开始上很重的第三方音频中间件，先用 Unity 原生音频完成第一版：

- 足够快
- 足够可控
- 和当前原型代码匹配
- 后面如果需要再迁移到 FMOD / Wwise 也有清晰事件层

最推荐的首个可交付版本是：

- 一个 `AudioService`
- 一套 `AudioCue ScriptableObject`
- 一个 `PlayerAudioBridge`
- 两三个 `WorldAudioEmitter`
- 一套 `SurfaceAudioProfile`

这样你这周哪怕素材只收了一半，系统也已经能开始接线和试调。
